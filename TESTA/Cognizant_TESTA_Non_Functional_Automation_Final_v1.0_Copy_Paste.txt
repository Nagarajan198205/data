Summary

Cognizant Worldwide Limited UK developed non functional automation for a UK government programme, connecting representative workloads, repeatable test preparation and transaction level analysis. PerfOps and Perf Insights help engineers assess capacity, resilience and the completeness of release evidence. Supplied reports show substantial load execution and expose transaction level failures that aggregate results can conceal. The team also reports reproducing abnormal cache growth missed by conventional tests. Separately evidenced IntelliA11y, IntelliSec and Intelliperf extend the engineering scope across accessibility, security and performance. Programme achievements, implemented capabilities and local demonstrations are distinguished throughout.

Main entry

1. Background, importance and goals

Cloud migration introduced distributed services and Kubernetes scaling into a UK government programme. Engineers needed to assess response times, capacity and resilience while reducing manual preparation, validation and reporting. Daily environment rebuilds removed test data and left a short window to recover infrastructure telemetry. A completed test was useful only if its workload was meaningful and its evidence sufficiently complete to support a decision.

Cognizant Worldwide Limited UK addressed these needs through PerfOps pipelines, cloud native performance testing and Perf Insights analysis. Performance specialists worked with development and environment teams to define workloads, investigate failures and repeat validation. Their goal was to make non functional assurance repeatable while keeping engineers responsible for diagnosis and release advice (N03 to N04).

The entry also covers innovation produced by this team and adopted as Cognizant Intelligent Platform, including IntelliA11y for accessibility, IntelliSec for security and Intelliperf for native performance execution. These are separately evidenced capabilities. The records do not establish their common deployment on the programme. Intelliperf is distinct from both PerfOps and Perf Insights. Evidence references separate programme narratives and anonymised screenshots (N01 to N04, N06 to N07), arithmetic reconciliation (N05), local demonstrations (A11 to A13), implementation inspections and provenance limits (A09 to A10, A14 to A15), and architecture (ARC01 to ARC04).

2. Approach and technology

The documented workload method begins with production traffic analysis. A reusable Kusto Query Language library examines request rates, transaction mix and peak periods to inform workloads and non functional requirements. The documented framework covers baseline, load, stress, spike, endurance and failover testing, including Horizontal Pod Autoscaler and Cluster Autoscaler behaviour. Application and infrastructure telemetry support investigation at pod, node and cluster level (N03).

PerfOps connects preparation, execution and validation through Azure DevOps. JMeter and Azure Load Testing supply programme workloads. Python routines check response time thresholds, error rates, throughput and capacity. The source describes scaling environments up before tests and down afterwards, with automated infrastructure assessment, HTML reports and alerts. Scaling down supports resource control, although no measured cost saving is supplied.

The delivery narrative describes six execution profiles covering smoke, peak load, scalability at 2x, 3x and 4x peak, and endurance. A shared preparation stage provides 16 data files for Azure Load Testing, alongside metric configuration across 64 Azure resources. Readiness checks are intended to distinguish an unavailable environment from an executed test. A profile driven .NET 8 generator creates related synthetic records across identity and business systems, with schema validation, retry with backoff, duplicate protection and per file verification (N04).

Perf Insights brings test outputs and telemetry into a common JSON summary for comparison and offline report regeneration. Stable run identifiers preserve traceability when files move. Its evaluation rules are deterministic. AI assistance in developing the tooling is separate from the logic that evaluates a run. The source describes six evidence sources, four output formats and approximately ten insight rules (N04).

The complementary products provide native engines with distinct roles. IntelliA11y combines repeatable DOM checks with optional AI assisted contextual assessment and specialist review. IntelliSec implements native security analysis and deterministic release gate checks covering severity, required controls, evidence and coverage. Incomplete or indeterminate conditions can prevent a favourable verdict. Intelliperf's inspected InternalRunner executes HTTP workloads, checks assertions and collects metrics with load control and runtime safety mechanisms, alongside AI assisted interpretation in its documented architecture (A10, ARC01 to ARC04).

3. Innovation

The engineering contribution is the connection between realistic execution and evidence that engineers can trust. Workload modelling addresses what to exercise. Automated preparation makes it repeatable. Resource level checks expose when the resulting report is incomplete. The delivery record describes runs previously considered successful even though 57 of 64 configured resources had supplied no telemetry. Seven of 64 configured resources (10.94%) supplied telemetry. Active versus idle expectations remain unresolved. Perf Insights makes incomplete collection explicit through a quality gate, configurable coverage requirements and a controlled override. This is a reported discovery of missing evidence, not a measured improvement in coverage. Gate retest records are not attached (N04 to N05).

The report also keeps aggregate performance separate from individual transaction requirements. A supplied load report summary displays P95 below its stated threshold, while its detailed findings identify 22 endpoints breaching the SLA at P95. A favourable overall figure cannot establish that every important transaction meets its requirement. The report brings together trends, transaction level checks, error classification, infrastructure correlation and prioritised findings to direct investigation (N06).

Across the products, automation supports accountable review. IntelliA11y implements expert review of pending false positive reports and conditional creation of an Azure DevOps work item. An installed generic ticket consumer provides a route to subsequent analysis. A completed chain through an accepted rule or model change, regression and an originating user rescan has not been demonstrated. Versioned prompts, usage recording and experiment machinery support controlled development, but do not themselves prove improved detection. Training code exists. Completed training to serving provenance and independent evaluation remain outstanding, so no achieved fine tuning benefit is claimed (A09 to A10, A14 to A15, ARC02).

4. Results and reported outcomes

The supplied performance analysis screenshots display a substantial workload record. Underlying raw execution data is not attached. A report labelled as a 3x load baseline shows a 60 minute steady state, 120 observed virtual users, 347,553 steady state samples and throughput of 96.5 requests per second. The summary displays P95 of 1.13 seconds against a 2 second SLA, with 71 failures. Detailed findings identify 22 endpoints breaching the SLA at P95, and visible transaction rows include sample counts of 32 and 67. The aggregate sample count therefore cannot be applied to every transaction (N06).

The same screenshot set also displays a distribution P95 of 2,403 ms and an error taxonomy containing 133 failed samples. Population and time window definitions are needed to reconcile these with the summary's 1.13 seconds and 71 failures. The exhibits show populated analysis and detected failures. They do not establish accepted NFR achievement, production comparability or a passing retest. The conflicting values remain explicit because their measurement populations have not been reconciled.

Separate exhibits show 7,532 requests against a 7,200 request target over 60 minutes, or 104.6% of target volume. Another alert flags P90 values of 5,134 ms and 4,943 ms against a 4,000 ms threshold, but contains only four displayed observations per transaction. These records support volume checks and threshold failure detection only. They are distinct from the larger N06 report. Neither run's sample size validates the other (N01, N05).

Pipeline screenshots show three completed workload jobs of approximately 1 hour 32 to 33 minutes each and an analysis job taking 1 minute 50 seconds, producing two artifacts. These are displayed execution durations, not a before and after measure of effort saved. A portfolio dashboard shows 11 projects, with six green, two amber and three red, with ten open bugs. A selected service is marked FAIL and at risk, with two open bugs. These views make incomplete assurance and unresolved defects visible in delivery discussions. They do not prove release approval or defect resolution (N07).

The programme narrative reports performance readiness inputs for three major releases and migration decisions, including issue identification before cutover and repeat validation after remediation. The delivery team reports more than 90% less manual effort separately for performance validation and infrastructure validation. Comparable task timings, including review and exception handling, are not supplied, so these remain attributed estimates rather than verified savings. Accepted retests and dated decisions are needed to verify release readiness. An observation window is needed for any post release incident claim (N03 to N04).

Local product demonstrations establish specific behaviours.

The unchanged IntelliA11y native engine was exercised twice on original and manually corrected HTML. Server side JSDOM analysis returned three confirmed finding records before correction and none afterwards. Review required findings changed from eleven to five, including one newly reported item. Two confirmed records concerned the same input, so these are not three independent barriers. Zero confirmed findings does not establish accessibility conformance. No LLM inference, rendered browser interaction or assistive technology assessment was used. Optional RAG enrichment was unavailable (A11). Separately, the team reports 85% accessibility activity automation. Eligible activities, numerator, denominator and measurement period remain unverified, so this figure is excluded from measured benefits.

One native IntelliSec PHP detector returned one finding for deliberately predictable token generation code and none after manual correction. Semantic AI and several broader stages were disabled, including a required structural stage despite file level coverage reading completed. This demonstrates the selected detector path, not a comprehensive application scan, a client security improvement or operation of the separate release gate (A12).

The unchanged Intelliperf runner sent real HTTP requests to a synthetic target. Three measured requests failed a response content assertion before a manual fixture correction. Three passed afterwards. HTTP errors were zero in both phases, demonstrating why successful transport and correct content require separate checks. Database, authentication and status integrations were isolated, and no model inference occurred. Three samples per phase support neither performance improvement nor sustained load claims. The correction was made by the evidence author, not an autonomous remediation service (A13).

5. Overcoming challenges

The delivery narrative reports daily loss of execution data, automated routine repopulation and manual recovery for exceptional partial creation failures. It also reports correcting failure paths that returned successful exit states and automating retrieval of current storage keys. These changes address specific causes of interrupted or misleading runs rather than merely accelerating a working process (N04).

Telemetry loss presented another challenge. A healthy looking report could conceal missing evidence. Resource level checks exposed the gap, and the completeness gate gave engineers a means to identify it within the short collection window. Distinguishing collection errors from idle resources is essential to interpreting that gate. Further controlled adoption of Perf Insights is planned (N04 to N05).

A production cache problem required a more realistic traffic model. Repeated requests to a public endpoint caused abnormal cache growth, but conventional browser like tests reused cached responses and failed to reproduce it. The team analysed logs, request characteristics and cache activity, then built a custom JMeter simulation with dynamic request fingerprinting and cache key variation to represent automated client traffic (N02).

The case narrative reports controlled reproduction outside production and validation of cache key normalisation, bucket segregation and retention changes with the development team. This provides a repeatable investigation method for a failure missed by ordinary traffic models. Paired numerical results under comparable workloads are still needed to quantify the reported cache reduction. Separately, migration testing reportedly exposed load balancing, session stickiness and subsystem integration issues, followed by remediation and repeat validation (N02, N04).

6. Sustainability and reuse

Reusable assets span workload analysis queries, execution profiles, synthetic data generation, automated checks, cache reproduction and evidence quality gates. The source describes a PowerShell utility for naming and think time updates in suites exceeding 1,000 requests. A console image shows sampler renaming output (N03, N07). Power BI views drawing on Azure DevOps Boards connect assurance progress and unresolved defects to delivery discussions. Neither capability carries a separately measured saving (N03).

Common JSON summaries, stable run identifiers and offline report regeneration help preserve the usefulness of collected evidence beyond a single execution. IntelliA11y, IntelliSec and Intelliperf are separately evidenced products, with source mapped architecture and local examples backed by internally retained reproduction harnesses. Common programme deployment is not established. Continued work focuses on controlled adoption, exceptional data recovery and linked correction to retest evidence. Engineers retain responsibility for interpreting findings, assessing unresolved risks and advising on release readiness.

Why this entry deserves the award

This entry demonstrates practical non functional automation built around difficult delivery conditions, including disposable environments, distributed infrastructure, misleading success states and traffic dependent failures. Its contribution combines repeatable execution with checks that expose missing telemetry and transaction level SLA breaches hidden by aggregate results. The supplied reports and bounded product demonstrations make that engineering tangible, while the distinction between reported achievements and verified observations gives judges a clear basis for assessment.
