Apply the two substantive fixes below before describing every solid arrow as an inspected path. Two small presentation refinements would improve precision.

1. Separate the CLI from the API pipeline on page 01.
Exact node 0 text: “Dashboard, API or CLI”. Its generated 0→1 edge then sends all inputs through “API controls and job intake”/workers and onward to common persisted issue/review records. Source F24 shows a separate CLI Puppeteer/JSDOM/bundled-engine path. No CLI-to-API-job or CLI-to-SQL-validation integration was established.
Narrow fix: node 0 line → “Dashboard or API request”; node 2 technology line → “Playwright / JSDOM (API path)”. Add note: “The separate CLI uses Puppeteer/JSDOM and a bundled rule engine; it is not shown entering this API workflow.” Alternatively add a separate CLI lane with its own local outputs and no invented link into the API queue/store.
Reason: the current combined input/technology node is individually true, but its explicit solid arrows overstate common orchestration.

2. Make conditional ADO transitions consistent with the stated optional-edge legend.
Page 01 currently generates 8→9 (“Expert validation”→“Configured ADO integration”) as solid. Page 02 draws 2→3 (“Expert decision”→“Create linked ADO story”) solid in the custom-edge block. The service only calls creation for an approved pending false-positive review, with configuration and success conditions. Rejection and trusted direct validation do not necessarily create a story; attachment can fail separately.
Narrow fix: draw these two arrows dashed/optional and label “approved pending FP; integration enabled”. Retain the source-implemented badge on ADO creation itself. In page 01 add (8,9) to optional/dashed; in page 02 change edge(2,3) to dashed and retain 0→1→2 solid.
This does not deny the implemented conditional call. It keeps the rendered legend's “dashed = optional” semantics and prevents an unconditional interpretation.

3. Optional badge precision.
Page 01 “Scan orchestration” and “Finding processing” receive “OWN ENGINE / SOURCE INSPECTED” because kind=core uses that global badge. These are owned orchestration/processing components, not themselves the accessibility detector engine. Use “OWN IMPLEMENTATION / SOURCE INSPECTED” for those nodes or reserve the engine badge for the locally registered rule engine. Do not change badge semantics for unrelated pages without their review.

4. Optional evaluation wording on page 02.
“Independent holdout + HTML cases” is correctly in a hand-off node, but distinguish requirements: independent holdout is needed for a comparative model-uplift claim; deterministic rule fixes can be checked through relevant positive/negative regression fixtures and broader regressions. Replacement: “Relevant HTML regressions; independent model holdout when applicable”. Do not imply a holdout has already been validated.
