INTELIPERF ARCHITECTURE — READ-ONLY SOURCE INSPECTION
11 October 2026; local repository ../aegis-test.

Conclusion
The inspected core implements its own workload executor, orchestration, runtime safety and deterministic result calculation. Calling that core merely a wrapper around a commercial load-test engine would misdescribe the inspected code. ScanRunner instantiates InternalRunner directly or dispatches to workers that instantiate the same class. Virtual users perform HTTP requests with native fetch; application code manages scenarios, sessions, extraction/assertions, scheduling, metrics and stopping. This supports the precise claim “a platform-owned execution and analysis engine built using standard runtime libraries and supporting imported test formats.” It does not establish originality against every competing product, production readiness, performance capacity, client deployment or delivered improvement.

Scope
Read-only source inspection; no tests, loads, scans, inference, external requests, database reads or product edits. No AGENTS.md found by scoped repository inventory. No client identifiers, target addresses, credentials or private feedback are reproduced. No history or runtime artifact was treated as a measured outcome. Inteliperf in this repository is separate from the client's PerfOps and Perf Insights work; none of their savings, release outcomes or test counts transfers to this architecture.

Status vocabulary for the companion diagram
I = implemented in inspected source; execution and effectiveness unverified in this task.
P = prototype implementation that simulates the claimed operational action.
D = intended/manual workflow; automatic end-to-end connection not established.
Every edge carries a status. Solid edges never mean proven deployment. References below are repository-relative; line ranges are review locators, and SHA256 fingerprints follow at the end.

1. Inputs and orchestration
JMeter and k6 compatibility paths convert imported scripts into canonical scenarios (P01/P02). These importers do not demonstrate native execution of arbitrary original scripts; conversion analysis explicitly identifies unsupported constructs. OpenAPI, HAR and manually specified inputs also have canonical plan-building code (P03). Names or legacy result fields containing k6 are not proof that k6 executes the primary scan.
Scan request routes contain quota, safety-mode, approval, collision and authentication checks (P04). ScanRunner applies load goals and safety caps, validates the plan, then chooses a worker or in-process execution path (P05). Worker execution imports the same InternalRunner and replaces progress/control adapters with Redis-based messaging (P06). This is actual source wiring, not an architecture-document claim.

2. Platform-owned execution and calibration
InternalRunner's VirtualUser executes scenario control flow, requests, assertions and extraction; HTTP requests use fetch (P07). Non-HTTP steps can delegate through protocol adapters. LoadControlEngine supplies schedules and step decisions; RuntimeSafetyMonitor is started by the runner and can terminate a run. Saturation and capacity checks can invalidate it. These mechanisms exist in source, but no runtime correctness or maximum-throughput benchmark was performed.
CalibrationService performs stepped concurrent HTTP probes and reads generator health (P08). It measures generator capacity/attempt rate, not service correctness: failed attempts are counted; missing usable targets trigger an estimated-capacity fallback. Calibration may be disabled. “Certified” in source is a platform-generated status, not external certification. This is neither model fine-tuning nor evidence that an AI model learns from runs.

3. Results, deterministic analysis and optional AI
The runner returns collected metrics and status; ScanRunner normalises results and persists them. The normalisation code invokes RiskEngineService directly (P05/P09/P10). RiskEngineService computes fragility, confidence, knee signals, threshold findings and ranked results without requiring a language-model call. This directly supports a deterministic core.
Separate chat routes call a configured language-model service and expose tool-assisted interaction (P11). A separate Lambda analysis path calls an analysis service or LLMAgent, with a metric-based fallback (P12/P13); its load generation is also native fetch. Do not collapse these alternative paths into a claim that every scan receives LLM analysis. Core collection/scoring does not depend on these LLM calls. “Optional AI interpretation alongside deterministic execution” is defensible; “no third-party dependencies” is not.
EvidenceSigningService contains manifest hashing, key management and signing/verification code (P14). This is an available service/API capability; the inspected core does not establish automatic signing of every completed scan. Signed evidence demonstrates identity/integrity when actually produced, not accuracy of the underlying measurements.

4. Feedback, remediation and retesting
NLIntentService persists intent feedback categories and notes (P15). This supports feedback collection, not a demonstrated training/update loop; no inspected feedback-to-model-retraining connection or improved parsing result was established.
Comparison code calculates differences between stored runs (P16). Its stated canonical-plan check uses projectId as a proxy and checks versions only when available. Consequently, do not claim it guarantees equivalent workloads. Human correction followed by another authorised scan and comparison is an intended workflow; no closed-loop before/after result was verified.
AutoRemediationService has playbook, approval, cooldown/rate-limit and audit structures, but uses in-memory maps. Crucially, both execution and rollback call simulateAction, using delays and random simulated failures (P17). Diagram these operational actions as prototype simulation. Do not claim automatic cache clearing, scaling, restart, rollback or proven remediation from this module.
CIReadinessService computes gate status using configured scores, confidence and failure counts (P18). Code existence does not validate release decisions. Overall and step PRS use different conventions; score meaning and formulas need correctness verification before presenting a uniformly interpreted risk scale or validated release gate. No product change is requested or performed here.

5. Market-tool boundaries and other prototypes
The core inspected execution path does not spawn k6 or JMeter. Import/conversion support and legacy-compatible result shapes coexist with the native executor. MultiRegionOrchestrator still contains mock regional-runner implementation (P19); it cannot establish distributed external-runner production capability. PerformanceTestAgent also generates simulated random results (P20) and must not be used as proof of real execution. The diagram anchors its native path to InternalRunner, not to that similarly named agent.

Recommended public description
“Inteliperf implements a platform-owned workload engine that executes canonical scenarios, collects measurements and applies deterministic analysis. It combines request execution with load scheduling, generator calibration and runtime safety checks, and supports imported test formats. Separate AI services assist interpretation and interaction. Source implementation establishes these mechanisms; deployment, measured benefits and operational remediation remain subject to runtime evidence.”

Remaining proof needed
An authorised representative run tied to the inspected version; persisted raw and normalised metrics; independent reconciliation of calculations; runtime worker/safety/calibration evidence; clear score semantics; evidence of actual signing if claimed; a controlled correction/retest pair with equivalent workloads; and original client outcome records for any client claim. No results are inferred from implementation alone.
