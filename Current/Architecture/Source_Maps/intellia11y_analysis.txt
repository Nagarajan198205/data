INTELLIA11Y ARCHITECTURE — SOURCE EVIDENCE MAP
Date: 11 October 2026. Read-only inspection of authorised repository only.

INTERPRETATION
This report maps implementation, intended human workflow and gaps separately. Source-present means code was inspected, not that it ran or deployed for a client. No tests, scans, external requests, model training or databases were executed/queried. No confidential identifiers, application URLs, credentials, dataset examples or feedback records are reproduced. Repository-root AGENTS.md was not found in the prior scoped inspection; no product changes were made.
The requested full lifecycle is a useful intended process. The inspected product supports several individual edges, but it is not evidenced as one automated, completed end-to-end improvement loop.

MAIN COMPONENTS
1. User surfaces: dashboard scan/issue/review/admin pages; browser verification bookmarklet; separate CLI. API scan intake, authentication/role checks and configurable device/scope/AI options mediate work.
2. Browser capture/execution: Playwright-based browser work, DOM/accessibility context and screenshots; quick/crawl/journey jobs and asynchronous LLM/screenshot workers. BullMQ/Redis provide queue/cache infrastructure. Browser/session readiness affects screenshots.
3. Owned accessibility analysis: API wrapper and locally registered IntelliA11y rules. Deterministic existence/validity and quality-pattern stages, grouping/deduplication, result tiers and confidence handling. Optional agent/model interpretation supplements them; the quick scan path disables the engine's internal LLM stage and uses separate agents.
4. AI services: prompt registry/version lookup, agent-specific context, optional model inference, usage/evaluation/improvement machinery and A/B comparisons. Model and embedding runtimes are external dependencies; their presence does not mean an adapted model is served.
5. Persistence/reporting: SQL issue/occurrence/validation and prompt/experiment records; Redis scan/screenshot caching; result/report APIs and dashboard views. Migration/source definitions do not establish populated production records.
6. Expert governance: trust-aware FP/confirmation submission, pending review queue, role-restricted approval/rejection, retained review fields and confidence recalibration.
7. Optional external work tracking: ADO story creation for approved pending FPs with a rule-versus-agent-prompt target and optional later screenshot attachment. Disabled/missing integration or failed upload can yield no work item/attachment.
8. Improvement branches: human/AI-assisted rule or prompt change; RAG content ingestion and retrieval; exported JSONL candidates plus standalone dataset/training/conversion scripts; HTML evaluation and existing regression-test definitions. These branches are distinct.

E02 Scan → screenshot-supported violation view
Source-present: F02/F03/F07. Element screenshot caching and delivery, DOM evidence and optional screenshot model context exist. Capture can be asynchronous or missing. ADO screenshot capture is a separate later live-page action; it need not reproduce the original scan state.

E03 Originating user marks potential false positive → pending expert review
Source-present: F08/F09/F10. Feedback maps to a validation status. Ordinary users' FP/confirmed/partial labels become pending_review; trusted roles apply immediately. Review rejection restores prior/open status. Expert decision is not identical to the user's requested label.
Runtime missing: aliased issue, submitting-role, requested-status, review-status and decision trail. No actual user feedback is copied here.

E04 Approved expert FP → ADO ticket
Source-present, conditional: F09/F10/F11. Approved pending FP calls story creation, conditional on integration configuration and success. Trusted direct validation does not follow the same reviewed-pending branch in the inspected flow. Creation and screenshot attachment are not atomic.
Runtime missing: permitted aliased review-to-work-item linkage, creation result, attachment success and failure handling. No credentials or application locations are needed in public evidence.

E05 ADO ticket → AI analysis of needed change
Partial: F11 embeds coding-assistant instructions and selects rule-file versus agent-prompt target. F12 separately reports FP patterns/suggestions. No ticket-consumption worker executing a coding assistant, applying a patch or closing the story was found in the inspected API source.
Runtime missing: a real human/assistant work record linked to the story, diagnosis, reviewed patch and approval. Draw this edge as human/AI-assisted, not autonomous.

E06 Analysis → rule-set or prompt update
Intended/manual intervention: F11 acceptance instructions name a source edit or Prompt Lab change; F13/F14/F15 provide prompt/experiment mechanisms. F09 also recalibrates rule confidence; confidence recalibration is not the same as changing a rule's detector logic. No automatic source rewrite/deployment was established.
Runtime missing: commit/prompt version before/after, reviewed rationale, matching regression output and applied release/configuration. A rule fix needs no model retraining when it changes deterministic logic.

E07 Analysis/expert content → RAG knowledge update
Source-present but separate workflow: F16 embeds reviewed/classified training chunks and records ingestion. F17/F18 retrieve vector context; F06 inserts retrieved content into agent prompts. No automatic ADO-ticket-to-approved-training-session bridge was established.
Runtime missing: approved content hash, ingestion IDs and backend, retrieval trace showing that content was used in the relevant prompt. Retrieval supplies reference context and does not modify model weights. F17's hybridSearch currently uses vector search, not demonstrated BM25 hybrid ranking.

E08 Validated content → dataset candidates → fine-tuning

F19 builds a split from source files 01–05; it does not read source 06_training_sessions, so seamless integration of that branch into the builder is not established. F20 contains actual QLoRA training code. F21 contains merge/conversion/registration code.
Runtime missing: approved dataset lineage and builder integration, completed training logs/checkpoints, adapter/model hashes and serving manifest. No completed training/served adapted model is proved by scripts. The prior evaluation-overlap finding remains adverse evidence; candidate export is not independent model evaluation.

E09 Rule/prompt/new model → sample HTML regression/evaluation
Source-present facilities, missing linked execution: F11 requests a regression test; F22 creates expected-behaviour HTML cases and invokes the configured model. F15 supports A/B results and comparisons. Test source/facility existence does not prove a regression passed, nor that a new model was selected or accepted. Configured-model evaluation is not necessarily a head-to-head comparison on a frozen independent set.
Runtime missing: issue-linked representative HTML fixture (permitted synthetic alternative), expected labels, source/model/prompt version, raw execution result, baseline/current results, independent review and regression scope. Synthetic fixtures verify tooling/behaviour, not client outcome or independent model uplift.

E10 Accepted fix → resolve/reassign external ticket
Intended manual step: F11 story description asks reassignment to the approving person when resolved. Inspected ADO code sets an optional initial default assignee but has no evidenced resolution/reassignment completion callback. F07 provides an internal issue-status update; this does not establish external ticket completion.
Runtime missing: actual work-item state/assignment history linked to accepted change, plus role-only acceptance record. Do not conflate internal fixed status with externally resolved or user-confirmed.

E11 Resolve/reassign → originating user rescans/confirms
Partial reusable capabilities: F01 allows a new scan; F23 allows known-issue confirmation/FP feedback from a bookmarklet. It fetches stored issues rather than proving a fresh rescan. No automatic notification/assignment to the original submitter, enforced fresh-rescan comparison or final closure gate was established.
Runtime missing: original anonymous submitter-to-new-run link, new build/version, absence/reclassification of the specific issue, submitted confirmation and final acceptance. This remains a human validation step in the intended process.

ENGINE OWNERSHIP AND EXTERNAL DEPENDENCIES
F04/F05 establish an owned rule registry/evaluation implementation. This is not merely an unmodified wrapper around an external scanner. Some rule headers explicitly cite concepts from established tools/standards, so “own engine” does not establish independent invention of every rule.
Playwright controls API browser work; the CLI uses Puppeteer. JSDOM parses DOM; queue/database/vector/PDF libraries supply infrastructure. These are external libraries, not all external accessibility detection engines. F25 declares an axe integration dependency. A wider first-party source search found an actual AxeBuilder import/call in the separate comparison script F27. This is an explicit comparator execution path, not an API/CLI scan engine. No axe invocation was found in the inspected primary API/CLI runtime TypeScript paths: API quick scan calls the owned engine (F02/F04/F05), and CLI imports createEngine at line 10 and calls it at lines 140–148 (F24). Thus the supported boundary is owned rules as primary scanning implementation, external axe in a separately invoked benchmark/comparison script. Do not depict axe as an optional ordinary scan engine or claim that the project never executes external scanners. CLI metadata mentioning pa11y is not proof that pa11y executes. API and CLI own-rule paths must be distinguished. Do not claim no external libraries, all criteria covered or standards conformance from these findings.
Fine-tuning changes model parameters through F20; RAG changes the context retrieved into a prompt through F16–F18/F06. Prompt edits and deterministic rule changes are additional separate mechanisms. Exporting, embedding, training, converting and serving are different states.
